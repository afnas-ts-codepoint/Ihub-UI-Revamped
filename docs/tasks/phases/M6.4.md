## Objective

Migrate the rendered Purchase Order experience (`poBody`) faithfully as a new `po` segment in the existing `/home/purchasing/:section?` route family, complete the Phase 3 gates, and stop for explicit human approval.

- PO tabs: to-do, history, report (`poSubDef`/`poSegBar`/`poInner`).

- Supplier Quotations (M6.5) is explicitly out of scope and was not implemented.

- Five findings were made during source reading, all resolved without deviating from the approved fidelity-first rule (see `DECISIONS.md` and `PROTOTYPE_DELTAS.md` for the full write-ups):
  1. **Outer nav-strip reconciliation (human-resolved, ADOPT).** M6.3 deliberately did not reproduce the prototype's outer 4-tab `pcSub` switcher at all (see `docs/tasks/phases/M6.3.md`, "Route map and shell integration"), because two of its tabs pointed at then-out-of-scope M6.4/M6.5 screens. Only Supplier Quotations (M6.5) remains omitted from the nav.
  2. **`poSub` stays local state, not new routes (non-blocking).** `poSub` (`index.html` 10109) is local `useState`, never part of a URL, unlike `reqSub`, which M6.3 promoted to real routes. Implemented `poSegBar`/`poInner`'s 3-way To Do/History/Report switch as an in-page segmented control inside the single `po` route (`PurchaseOrderView`), matching the prototype's own non-routed behavior.
  3. **History tab renders no `RecordFilter` (non-blocking, literal fidelity).** Unlike Request History and unlike PO's own To Do/Report tabs, `poInner`'s history branch (`index.html` 10352) renders no filter at all. Preserved as a deliberate omission.
  4. **Attach dialog has zero validation on either button (acceptance-critical, literal fidelity).** `poAttachModal`'s Cancel and "Attach purchase order" buttons (`index.html` 10399-10400) both call the identical `setPoAttach(null)`. Missing captions, a blank PO number, and a blank actual value never block either button. No gating was added to either control.
  5. **"Drag and drop" copy is dead text (non-blocking, literal fidelity).** The file-picker label (`index.html` 10392) reads "Click to upload or drag and drop", but there is no `onDrop`/`onDragOver`/`onDragEnter` anywhere in `poAttachModal`. Implemented click-to-pick only; the misleading copy is preserved verbatim, not corrected.
- Fixture verification: `poRows` (4 purchase orders) and `poHistRows` (3 history rows) were read and ported verbatim — exact ids, suppliers, PC refs, values, dates, statuses and tones. The To Do tab's literal `Open 3` / `All 142` counts (unrelated to the 4 actual rows) and the History tab's derived `All 3` count (`poHistRows.length`) were both preserved with the same derived-vs-literal distinction as source.
- Shared-filter-state architecture note: the prototype binds every PC-related `RecordFilter` (Requests/PO/Quotations) to one shared `pcFilter` state. M6.3 already restructured Purchasing into independent routed views, each owning its own local `RecordFilter` state (`TodoRequestsView`, `RequestHistoryView`, `ReviewRequestsView` each have their own `useState(createEmptyRecordFilter)`), so cross-section filter sharing was already not preserved before M6.4. `PurchaseOrderView` follows this same established M6.3 precedent (its own local `todoFilter`/`reportFilter` state) rather than introducing new shared filter infrastructure across features/routes, which would be exactly the kind of speculative shared-state plumbing G8 warns against. This is a continuation of an existing, already-approved M6.3 architectural decision, not a new one.

## Delivered Behavior

### Route map and shell integration

- `/home/purchasing/po` renders the new Purchase Order segment; the 9-item segment pill bar (8 existing + `po`) mirrors the flat-bar precedent M6.3 established, with the same `Link`/`aria-current`/Back-navigation behavior as every other segment.
- Invalid section slugs continue to render the approved 404 page; `/home/purchasing/{create,pending,edit,review,todo,missing,history,report}` are unaffected.

### Purchase Order segment

- **To Do** (default): no `SectionHead` (fall-through, matching Requests' To Do precedent), `RecordFilter kind="request"` (own local filter state, per the M6.3 precedent above), and a `TabbedTable` with literal `Open 3` / `All 142` tabs (unrelated to the 4 actual rows) over `purchaseOrderColumns` (PO #, Supplier, PC Ref, Value KWD, Issued, Status pill, "Attach Purchase Order" row action).
- **History**: `PurchasingSectionHeading` ("History" / "السجل"), no `RecordFilter`, `TabbedTable` with a derived `All 3` count over `purchaseOrderHistoryColumns` (date, PO #, action pill, by, note) against the verbatim `purchaseOrderHistoryRows` fixture.
- **Report**: `PurchasingSectionHeading` ("Report" / "تقرير"), `RecordFilter kind="request" noExport`, and the permanent inert dashed-border placeholder ("Run the report to generate results. The table will render here." — the same literal string as every other Purchasing/Budgeting report placeholder).
- The To Do/History/Report switch is a local segmented control (`segmentedOptionClass`) inside `PurchaseOrderView`, not new routes — see Preflight finding 2.

### Attach dialog (`PoAttachDialog`)

- Opens from the To Do row action only, seeded with `{ po, supplier, pcRef, pcTitle, pcDept, pcValue, pcStatus }` looked up from `purchaseRequestRows` by `ref`; `poNo`/`actual`/`remarks`/`files` are `PoAttachDialog`'s own local state, fresh on every mount.
- Recap card ("Request details", "Read only" badge): Request #, Supplier, Department, Approved value (KWD), Committee status, Subject — all read-only, sourced from the seed.
- `AttachmentList`: each row shows the (non-editable) filename, a caption input whose border is `border-bad` whenever the caption is empty/whitespace-only (recomputed live on every render, not tied to submit) and `border-line` otherwise, and a remove control; a click-only file picker (hidden `<input type="file" multiple>`) appends new files with a blank caption. No drag-and-drop is wired — see Preflight finding 5.
- PO Number (`placeholder="PO-2025-000"`) and Actual purchase value (`inputMode="decimal"`, `placeholder="0.000"`) are plain editable text inputs, both initialized blank with no derivation from the approved value. Remarks is a plain 3-row textarea.
- **Cancel and "Attach purchase order" are functionally identical**: both just close the dialog, with zero validation of captions, PO number, or actual value — see Preflight finding 4. This is the single most important fidelity requirement in this phase and was implemented with no gating whatsoever.
- The dialog uses the same `DialogRoot`/`DialogContent` Radix primitives as `ReviewDialog`, so outside-pointer-down/Escape dismissal and body-scroll-lock are inherited from that already-approved shared primitive, not reimplemented locally.
- Reset-per-open is structural: the dialog is only mounted while a seed is non-null, and every row-action click builds a brand-new seed object, so re-opening — including the same row — always remounts with fresh blank state. No `useEffect`-based reset exists, matching the prototype's own mechanism exactly (mirrors `ReviewDialog`'s established M6.3 pattern).
