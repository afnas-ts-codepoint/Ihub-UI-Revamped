## Review Findings

**Analysis.** The prototype has exactly one live configurable dashboard: `tasks` (`ADMIN_DASHBOARDS[].live: true`, `window.setTaskDashConfig`, `ihub:taskdash`, `taskDashEffective`). Home/Finance/Action sheet/Petty cash are `live: false` ("applies once it goes live"). The prototype's Overview is a fixed layout that never reads a widget config, and its sections do not correspond to the 12-widget `home` catalogue. Role/Department/User scoped saves have no runtime consumer (PROTOTYPE-NOOP, M11.2).

**Human decision (2026-10-03):** M11.3 is *Tasks only, prototype-faithful*: Default + personal layers reach the Tasks dashboard; Overview stays fixed; Role/Dept/User scopes stay authoring-only. See D34.

**Architecture (single source of truth).** The Tasks runtime store `taskDashboardConfig.store` (M8.2, key `ihub.v2.taskdash.config`) owns the `tasks` dashboard's organisation Default and personal layout, mirroring the prototype's `ihub.taskdash.default` / `.me`. `useDashboardBuilder` (settings) reads and writes them through the tasks public API (`useTaskDashboardConfigStore`, `sanitizeTaskDashboardConfig`; the allowed settings-to-tasks import). Non-default scopes and all other dashboards remain in `dashboardConfig.store` (the prototype's `ihub.taskdash.scopes`). Because both sides are Zustand stores the dashboard updates live without `window.*` events. `TaskDashboard` already rendered `effectiveTaskDashboardConfig(org, personal)` and is unchanged.

**Widget mapping.** The Settings catalogue ids equal `TASK_DASHBOARD_WIDGET_IDS` one-to-one (metrics, slaPerf, compliance, source, dependency, highPri, byDept, matrix, impacted, critical, workload) and map to the `TaskDashboard` widget map.

**Precedence.** Effective layout = personal layer filtered to the Default's ids; Default `hide:false` force-appends missing ids; `dnd:false` forces Default order; `lock` re-adds mandatory `metrics`/`slaPerf`; columns come from the personal layer, else the Default. A parity test proves the builder's `sanitizeUserConfig` and the runtime `effectiveTaskDashboardConfig` agree. Unknown ids are dropped; invalid `cols` or non-boolean flags fall back (stricter than the prototype's raw pass-through).

**D23-D26.** D23 (preview) - retained: the preview stays schematic (embedding the real dashboard is not in the approved M11.3 scope, and the card forbids changing the M11.2 UI). D24 (cross-feature wiring) - resolved: replaced by the shared store, no `window.*`. D25 (drag handle a11y) - retained. D26 (flash/fixture text) - retained.

**Files.** `features/tasks/store/taskDashboardConfig.store.ts` (export the sanitiser), `features/tasks/index.ts` (public API), `features/settings/hooks/useDashboardBuilder.ts` (runtime read/write), `features/settings/pages/DashboardRuntimeIntegration.test.tsx` (new, 16 tests), `tests/visual/m11.3.spec.ts` and the `visual:capture:m11.3` script.

**Quality gates.** Focused settings/tasks/home: 42 files, 566 tests pass. Full regression: 151 files / 1,486 tests pass. Typecheck and lint: only the pre-existing M8.3 findings (`CreateTaskPage.test.tsx:93`; `CreateTaskForm.tsx` 380/450). `vite build` and `check:bundle` pass. `report:pending` runs with no new markers. Vitest reports one unhandled `vaul` `setPointerCapture` jsdom error in a Home drawer test (pre-existing, unrelated), and the pre-existing M11.2 React "setState while rendering DashboardBuilder" warning is unchanged. Visual QA: 11 Playwright runs (organisation and personal layers x EN/AR, Paper/Ink, 1440/760/390 side by side with the prototype, plus the Settings save/reload flow); evidence in `docs/migration/qa/M11.3`; widget set, order and columns match the prototype; remaining differences are pre-existing M8.2 ones.
