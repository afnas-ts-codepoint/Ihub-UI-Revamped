## Plan/prototype reconciliation

The M3.4 phase card (and the migration-plan wording it was drawn from) referenced `FilterForm` and a stat row for the Notifications page. Direct inspection of the current prototype source found both references did not match actual `NotificationsScreen` behavior:

1. **Filter component.** `NotificationsScreen` (12032-12129) renders the shared `RecordFilter` with `kind="history"` (line 12098), not `FilterForm`. `FilterForm` (7947-8069) is used exactly once in the whole prototype — inside `ReportsScreen`/"Analytics & Reports Library" (line 9709) — which is explicitly out of scope for M3.4 ("Do not begin Reports Library work"; that belongs to M3.9).
2. **Stat row.** `NotificationsScreen`'s full function body (12032-12129) contains no `StatRow` call. `StatRow` is used by other screens (Overtime at 8440, others at 11290/11492/11548/11559/11591) but never by Notifications.

Both discrepancies were surfaced to the human reviewer before implementation began. Decision (2026-09-26, recorded in `docs/migration/DECISIONS.md` and `docs/migration/PROTOTYPE_DELTAS.md`): **ADOPT current prototype behavior** in both cases. Implementation therefore:

- Reuses the existing shared `RecordFilter kind="history"` and does not create an unused Notifications-local `FilterForm`.
- Renders no stat row/`StatTile` cards, since none exist in the current prototype source.

`FilterForm` extraction/promotion remains untouched and deferred to M3.9, subject to that phase's own delta intake.

## Data model note (page vs. bell)

The Section-view notification-log rows (email/subject/status/type/date, an outbound-delivery log) are a structurally different dataset from the M2.3 top-bar bell/menu rows (`subject`/`time`/`tone`/`type`, `LocalizedText`, per-item `isUnread`) — this divergence exists in the current prototype itself, not introduced by migration: `NotificationsScreen`'s five rows are a subset of the bell's eight subjects by topic (three SLA/urgent bell items have no page-log row at all), and the page's `status` field (delivery status) is unrelated to the bell's `isUnread` flag. Per the standing rule not to force datasets together where the prototype itself does not, the page uses its own `NotificationLogEntry` type/mock/hook (`notification-log.types.ts`, `notification-log.mock.ts`, `useNotificationLog`) inside the same `src/features/notifications/` feature folder, alongside the unmodified M2.3 bell data (`notifications.types.ts`, `notifications.mock.ts`, `useNotifications`). Both live under one feature-owned source of truth (the `notifications` feature); no second feature folder was created and no existing M2.3 file was duplicated or altered.
