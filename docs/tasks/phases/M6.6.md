## Deviations

- **Activity/Sub Activity master data duplicated, not reused from Purchasing.** The prototype's `CreateActionSheetPanel` reads the same global `window.ACTIVITY_NAMES()`/`SUBACTIVITIES_FOR()` helpers Purchasing's `PCRequestCreate` uses. Production architecture (`eslint.config.js` `no-restricted-imports` feature allowlist) permits `src/features/payment-settlement` to import only `organization`, not `purchasing` — the same G8 "no forced cross-feature reuse" rule Purchasing itself already followed relative to Budgeting's identical fixture (see `docs/migration/DECISIONS.md`, Purchasing's `activity-master.fixture.ts` doc comment). A feature-local copy (`data/activity-master.fixture.ts`, `domain/activityMaster.ts`) was added, trimmed to only the name/sub-name lookups Action Sheet needs (no budget/committed amounts, since Action Sheet's "Budgeted" field is a manual Yes/No toggle, not a computed availability).
- **`ACTION_SHEET_FX` kept deliberately distinct from Purchasing's `CBK_RATES_KWD`.** The prototype hardcodes a separate local FX table per screen (`EUR` 0.335 vs Purchasing's 0.334, `SAR` 0.082 vs 0.0819, `GBP` 0.39 vs 0.392) — preserved exactly, not reconciled.
- **`RecordFilter kind="sheet"` reused as-is for Action Sheet**, even though its configured categories/subcategories/status options (`reference-filters.mock.ts`) were authored for Checklist's Audit Sheet semantics (M3.5) and do not literally match Action Sheet's own category (`Regular`/`Scheduled`) or status (`Draft`/`Submitted`/`Returned`/`Paid`) values. This is not a migration defect: the prototype's own `RF_KIND.sheet` object (`index.html:L1295-1297`) is the exact same metadata reused verbatim by both `ChecklistScreen` (`kind:'sheet'`, L6537) and `ActionSheetSection` (`kind:'sheet'`, L17288) in the source — the mismatch is a pre-existing prototype quirk, adopted rather than silently fixed.
- **Edit row action preserved as a real (if odd) behavior, not treated as inert.** Unlike Purchasing's `reqActBtn` (confirmed dead — no `onClick` at all), Action Sheet's `editCols` row action does call `onClick:()=>setSub('create')` (`index.html:L17187`) — it switches the parent tab strip back to Create without loading the row into a draft. Implemented via an `onEditRow` callback prop from `ActionSheetSection`, not as a no-op.
- **Row fixture values (`status`/`action`/`type`) stay literal English only**, even though the prototype technically wraps them in `T(en, ar, locale)` with real Arabic counterparts (e.g. `statusAr:'مسودة'`). This follows the already-established, broader codebase convention (Purchasing, Budgeting) that table row *data* values are never re-translated in production — only chrome, labels and headings are. Confirmed this is the existing pattern, not a new one, before applying it here.
- **Report view renders its own bespoke Year/Department/Type/Status/From/To fields, not the shared `RecordFilter`.** Unlike every other Action Sheet sub-tab, the prototype's own `reportView` (`index.html:L17272-17285`) does not render `asRecFilter` at all — it has a separate local field block. Both "Generate report" and "Export to Excel" have no `onClick` in the source and stay inert (`PROTOTYPE-NOOP(D2)`), matching the M3.9/M6.1/M6.2/M6.3 permanent-inert-report-placeholder precedent.
- **`ActionSheetForm`'s `review`/`resubmit`/`verify` code paths are unreachable in this phase.** Per the phase's own scope line ("`ActionSheetForm` exported for Home"), the component was built to support all four modes and is exported from the feature's `index.ts`, but no route in M6.6 invokes it with `review`/`resubmit`/`verify` — that only happens once the Home approvals queue (M10.1, `DashboardOCC`'s `formModal`) is built. This mirrors the already-accepted pattern of M6.4/M6.5 exporting components ahead of a still-pending consumer.
- **`petty-cash` and `add-supplier` remain `MigrationPending`** inside the new three-tab `HomePaymentSettlementPage` shell (same shell, inert other two tabs), exactly matching the M8.1→M8.2 Dashboard-tab precedent of shipping the shell before every tab has real content. `router.tsx`'s `paymentModules` allow-list was replaced by `isHomePaymentSettlementModule`/`HOME_PAYMENT_SETTLEMENT_MODULES`, preserving identical reachability (three allowed modules, `NotFoundPage` otherwise).
