| D21 | Task View header — Work Progress % | `TaskEditPage` recomputes progress from its own local `checked`/`JO_CHECKLIST` seed (`item.id`-derived), independent of any other screen's progress figure for the same task. | Task View reuses the already-established `TaskViewModel.progress` (checklist-count-derived, computed once in `tasks.store.ts` and already shown by M8.1's list/board/`TaskDetailDialog`). | Avoids a second, divergent progress calculation for the same task id across the app; M8.4's own header stats (Response/Verification/Resolution/Completion) and started/target dates are still ported as literal seeded values, only the checklist-progress % is reused. | Minor, intentional | Implemented during the M8.4 (Task View) run, 2026-09-29; not separately human-approved — reported for review alongside the rest of the phase | 2026-09-29 |
| D22 | Task View — unknown task id | The prototype has no unknown-task-id case reachable through normal navigation (`TaskEditPage`'s only "no item" branch is a stale in-memory ref recoverable only via a page refresh, and it shows a generic "No task selected." message with a Back button). | `/tasks/:taskId` for an id absent from the tasks store renders a dedicated not-found state (icon, "Task not found" / "المهمة غير موجودة", a short description, and a "Back to tasks" action), matching this codebase's existing `NotFoundPage` tone rather than the prototype's generic message. | M8.4 is a real, directly-linkable route (unlike the prototype's client-side-only state), so an unreachable/mistyped id is a realistic case that needs its own state; the existing `NotFoundPage` copy/tone was used as the closest in-codebase precedent instead of inventing new copy from scratch. | Minor, intentional | Implemented during the M8.4 (Task View) run, 2026-09-29; not separately human-approved — reported for review alongside the rest of the phase | 2026-09-29 |
| D23 | Settings — Configuration live preview | The prototype's `TaskDashPreview` renders the real, functioning embedded Task Manager dashboard (`window.JobOrdersScreen`, `dashCfg` prop) scaled to fit, for the live `tasks` dashboard specifically; the other 4 dashboards get a schematic `WireDashPreview` instead. | M11.2 uses one placeholder/schematic preview (`DashboardSchematicPreview`: label, icon, size-driven grid tiles) uniformly for all 5 dashboards, including `tasks`. | Rendering the real, functioning Task dashboard inside a config-preview pane is genuine runtime integration, which the M11.2 phase card itself scopes out ("Runtime integration ... is deferred to M11.3"); M8.1-M8.4's approved Tasks feature is not reused or duplicated here. | Minor, intentional | Implemented during the M11.2 run, 2026-09-29; not separately human-approved — reported for review alongside the rest of the phase | 2026-09-29 |
| D24 | Settings — Configuration cross-feature wiring | Saving the Default scope for the live `tasks` dashboard calls `window.setTaskDashConfig` and dispatches a `window.dispatchEvent(new Event('ihub:taskdash'))` global event that the real Tasks dashboard listens for. | M11.2 has no `window.setTaskDashConfig`-equivalent global and dispatches no cross-feature event; saved configurations are held entirely in the feature's own Zustand store (`dashboardConfig.store.ts`) and never read by the Tasks or Home Overview features. | `window.*` communication between features is disallowed in this codebase (see `AGENTS.md`); M11.2 is explicitly scoped as prototype-visible UI on local/mock state, with runtime integration into `taskDashboardConfig.store` and the completed Task/Overview dashboards deferred to M11.3 once its own dependencies (M8.2, M10.2) exist. | Minor, intentional | Implemented during the M11.2 run, 2026-09-29; not separately human-approved — reported for review alongside the rest of the phase | 2026-09-29 |
| D25 | Settings — Configuration widget drag handle accessibility | The widget list's drag handle (`I.dots`) has no ARIA role, no `aria-label`, and no keyboard-operable reorder fallback — reordering is only possible via a mouse-driven native HTML5 drag-and-drop gesture. | M11.2 preserves this exact gap: the drag handle carries no additional ARIA semantics and no keyboard alternative was added. | This is a genuine, pre-existing prototype accessibility gap, not something to silently "fix" by inventing a keyboard-reordering mechanism the prototype itself does not have; the toggle/switch/radio ARIA semantics the prototype *does* have (checkbox role+aria-checked+aria-label on hide/show; role=switch on the rule toggles; role=radiogroup/radio on scope and column selectors) are all preserved. | Minor, intentional (fidelity preservation) | Implemented during the M11.2 run, 2026-09-29; not separately human-approved — reported for review alongside the rest of the phase | 2026-09-29 |
| D26 | Settings — Configuration save-flash / fixture text asymmetry | Several English save-flash strings interpolate the dashboard label (e.g. "Saved — the {dashboard} dashboard now uses this layout"); their Arabic counterparts are generic, non-interpolated text. The saved-configuration library seed's `name`/`applied`/`by` fields, and the Role/Department/Individual-user target lists (`ROLES`/`RF_DEPTS`/`USERS`), are plain hardcoded English strings with no Arabic counterpart at all. | M11.2 preserves both asymmetries exactly: the `settings.json` locale pair keeps the EN-interpolates/AR-generic flash-copy split, and the `ROLES`/`USERS`/saved-library fixture text stays untranslated plain strings in both locales (matching the prototype; `RF_DEPTS`'s already-migrated equivalent, `REFERENCE_FILTERS.departments`, is reused rather than duplicated). | These are genuine untranslated-completeness gaps in the prototype itself, not something to improve; "fixing" them would be an undocumented behavior change beyond this phase's scope. | Minor, intentional (fidelity preservation) | Implemented during the M11.2 run, 2026-09-29; not separately human-approved — reported for review alongside the rest of the phase | 2026-09-29 |
